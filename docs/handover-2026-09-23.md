## 1. What shipped

| Table | What it holds |
|---|---|
| `courses`, `course_items` | Vetted YouTube sequences. **No `child_id`** — shared library content |
| `course_assignments`, `course_item_progress` | One child's journey through one course |

`memory`. New client: `youtube_client.py` (search + metadata, mirroring
`gemini_client.py`'s "one module knows the wire format" shape).

### The agent layer

One model call per message. System prompt is rebuilt every turn from live
DB queries. Returns prose **or** one function call. No agent loop.

Seven tools, **none of which write anything**:
`draft_task`, `draft_event`, `ask_follow_up`, `open_block_picker`,
`propose_reflection`, `generate_course`, `draft_special_task`.

Two of them do real work before replying (`generate_course`,
`draft_special_task`): real YouTube search → real metadata → a **second,
separate** Gemini call that vets and orders the results. That is the only
multi-hop reasoning in the system.

## 2. Decisions that are load-bearing

**The model never writes.** Every tool either opens a card or produces a
draft; a parent's tap is what mutates. This is the invariant the whole
design rests on — it keeps a misunderstood request at "wrong draft shown"
rather than "wrong thing done to a child's phone." Confirmed with the user
when they asked for more autonomy: reason fully, still one tap.

**Courses split content from progress.** Vetting is expensive (a search
plus an LLM pass); assignment is cheap. So `courses` is shared with no
owner, and `course_assignments` is per-child. A sibling gets the same
vetted course with no repeat search. A shared row is never mutated by a
child's progress.

**A `course_assignment` belongs to exactly one consumer** — a reflection,
a task, or a milestone. Never two. If a reflection and a task shared one,
finishing it for one would silently finish the other.

**Memory is rows, not embeddings.** A parent has to be able to read and
delete what this believes about their child, and you cannot show someone a
vector. At a few dozen facts, retrieval is "put them in the prompt."
Revisit pgvector past a few hundred facts per child, not before.

**Memory holds only what has no column.** Bedtime lives in
`child_rules.downtime_start`; a remembered copy is a second source of
truth that goes stale. Memory is for preferences, family context, what
worked. The extraction prompt enforces this and it holds live.

**Reflection is an independent gate.** Pending reflection locks the device
regardless of task status, and clearing it doesn't satisfy tasks. Both
must clear on their own.

**A child's milestone proposal carries no prize.** The propose schema has
no prize field at all — not ignored-if-sent, absent. The prize is screen
time; a child writing their own would undo the point of the app.

**Asking is a tool, not prompt prose.** `ask_follow_up` has a schema; the
alternative — "ask if you're unsure" in the system prompt — was explicitly
rejected. It renders as a plain message with **no card and no suggested
answers**: chips were tried and removed, because offering tappable answers
turns an open question into multiple choice and puts the model back to
guessing what the task might be. The point is to ask, then listen.

## 3. Bugs found, with root causes

These explain code that otherwise looks arbitrary.

**The Add Task card was empty on every AI request.** The model returned
clean structured args; the code flattened them into an English sentence and
re-parsed it with string matching, looking for `" to "` *with a leading
space* against a string starting with `"to "`. Proven by running the real
parser over real tool output. Fixed by not round-tripping through prose —
`TaskDraft` carries structured values. `AddTaskCard.parse` is deleted.

**The model never knew today's date.** `_system_prompt` queried
`date.today()` for occurrences but put no date in the prompt, so "tomorrow"
resolved against the training cutoff. One line; everything about relative
scheduling was guesswork before it.

**`handleAddTask` never sent the due date or time to the API.** A second
layer of the same bug — even a correct card lost the schedule.

**Two approval paths, one with side effects.** `PUT /occurrences/{id}/status`
set status directly and never called `_review`, so approving through it
skipped the task bonus — and would have skipped app-block resolution and
milestone progress. Both funnel through `_review` now. Do not add a third.

**`submission_kind = 'course'` was rejected twice, silently.** A live CHECK
constraint from the original schema, *and* `_safe_submission_kind` coercing
unknown values to `"none"` with no error. Both fixed.

**The dead `app.reflections` table.** `evlin-tables.sql` had one with
totally different columns. `CREATE TABLE IF NOT EXISTS` would have
silently no-opped against it, leaving the model pointing at columns that
don't exist — **green tests, 500s in production**, because tests build
their schema from `models.py` and never run migrations. Renamed to
`reflections_legacy` rather than dropped.

**Milestone progress had no trigger.** Nothing defined which task
completions counted. Closed with `tasks.milestone_id`.

**The chat sidebar was fiction that overwrote fact.** Selecting a mock row
replaced the real transcript with invented messages; "New chat" only
cleared the screen. Replaced with real threads.

**The calendar review deck paged through a child's entire task history**
regardless of which day you opened it from. Now scoped to the day, derived
from the day's own rendered events so it can't disagree with the screen.

**`-1004` was reported as "Couldn't reach the server".** That's
`cannotConnectToHost` — usually the user's connection, not the server,
which was healthy at the time.

**The Gemini key was a blocked Vertex Express trial key** (`AQ.` prefix),
and `gemini-2.0-flash` had been retired. Now the project's real key and the
`gemini-flash-latest` alias, so a rotation can't break it the same way.

## 4. Traps for the next person

**Tests never run migrations.** `conftest.py` builds from `models.py` via
`create_all`. A model without a matching `_MIGRATIONS` entry is a table
that doesn't exist in production and the suite will not tell you.
`test_every_new_table_has_a_migration_matching_its_model` guards the newer
tables. `SlideLesson`/`ComicGuide` are already broken this way —
pre-existing, out of scope, don't copy them.

**Background tasks need their own session.** `extract_memories` opens
`SessionLocal` because the request's session is closed by then. In tests
this *bypasses the `get_db` override* and would make real Gemini calls —
an autouse fixture in `conftest.py` disables extraction by default.

**`~/.zshrc` has three `GEMINI_API_KEY` lines, one of them the old blocked
key.** `load_dotenv()` does not override existing env vars, so the shell
copy shadows `.env` entirely. Rotating the key in `.env` alone will appear
to do nothing. Worth deleting all three.

**`kind='streak'` is a lie.** `_bump_milestone_progress` adds 1 per
approved task regardless of day, so two tasks on one Tuesday count twice
and a missed day doesn't reset. It's a count wearing a streak's label, and
the parent UI offers "Days in a row". Either implement consecutive-day
logic (`last_credited_date`, reset on gap) or remove the toggle.

**The iOS project lists sources explicitly.** New files need
`xcodegen generate` or they won't compile in.

**SourceKit diagnostics in this repo resolve against macOS** and report
mass false errors (`Cannot find type 'UIViewRepresentable'`). Trust
`xcodebuild`, not the inline diagnostics.

## 5. Verified vs. not

**Verified against the live model, not mocks:**
- Tool routing across all seven tools, including event-vs-task
- Relative dates ("tomorrow at 6pm" → correct date + 18:00; "every school
  night" → Sun–Thu)
- Course vetting rejects age-restricted, off-topic and university-level
  candidates and never invents a video id
- Memory refuses character judgements ("lazy and defiant" → records
  nothing) and defers to DB columns
- Vague requests ask a follow-up; specific ones still draft directly

**Verified other ways:** 182 backend tests; the Swift screen-time budget
checked case-by-case against the Python implementation; the chat backfill
confirmed against the production database (it was a no-op — `chat_messages`
was empty, because chat had never worked in production).

**Not verified: any UI rendering.** No simulator interaction was possible.
Everything compiles; nothing has been seen on screen. Treat every screen
added here as unreviewed.

## 6. Open

**Blocked on a human:** `GEMINI_API_KEY` and `YOUTUBE_API_KEY` are not set
in Render's dashboard, so chat 503s in production regardless of what's
merged. No Render credentials available locally.

**Nine endpoints have no UI caller.** Worst first:
- `createReflection` / `reviewReflection` — **a parent can neither create
  nor approve a reflection.** `ScreenProfile`'s reflection card is still
  mock (`child.reflection?.review = "approved"`). A kid can complete one
  and it would sit in `submitted` forever.
- `createAppBlock` — `app_blocks` has no writer, so "no YouTube until
  homework's done" can't be set up, though resolve-on-approval works.
- `fetchCourses` / `assignCourse` — no library browser; courses only reach
  a child via a chat proposal.
- `generateMilestone`, `searchVideos`, `createSingleVideoCourse`,
  `deleteMilestone`.

**Deliberately not built:** real `ManagedSettingsStore` /
`DeviceActivityMonitor` enforcement. Everything drives the in-app lock. The
data layer is shaped for it — `EnforcementState` is one `nonisolated`
derived function over cached rows, and `LocalStore` already uses the App
Group container so an extension in a separate process can read it. **The
App Group capability must be enabled in the developer portal before the
next device build**; Simulator is unaffected.
