# Evlin

A parental-control app where screen time is earned by doing tasks. One iOS
app with two modes chosen at first launch:
- **Parent (iPhone):** tabs are Home, Chat, Profile (the child's; Settings is
  behind its gear). Profile's tab icon is a filled clock, the child's screen time
  (2026-11-12; an hourglass the same day, a person in a circle before).
- **Kid (iPad or iPhone):** tabs are Tasks (what opens the iPad) and Goals
  (`Tablet/ScreenTabletGoals.swift`, apart from the lock). On a phone the Tasks tab is
  the iPad's page in one column: greeting with the gear beside it, the play-time
  card, Today (2026-11-12; the card sat above the page on black, over a
  navigation bar holding only the gear).

The backend is FastAPI on Render with Postgres on Supabase and photos on
Cloudflare R2.

| Path | What |
|---|---|
| `Evlin/` | SwiftUI app. `Data/` holds the API client, sync, the SwiftData cache and the enforcement state. `Parent/`, `Tablet/` (kid), `Onboarding/`, `DesignSystem/` |
| `evlin-backend/` | FastAPI app (`main.py`), `routers/`, `models.py`, `schemas.py`, `tests/` |
| `evlin-backend/tool_calls/` | Every tool the chat AI can call, one file each, with a README listing them |
| `docs/` | Handovers and architecture notes. Older ones carry a note saying what's out of date |

## Builds: real vs Demo

There are two apps, and demo data must never reach the real one.

| Scheme / config | App | Who | What's in it |
|---|---|---|---|
| `Evlin` / Debug | Evlin (`com.evlin.ios`) | the user, Run in Xcode | real features only, real server |
| `Evlin` / Release | Evlin (`com.evlin.ios`) | Archive, TestFlight | real features only, real server |
| `Evlin Demo` / Demo | Evlin Demo (`com.evlin.ios.demo`) | agents, Simulator only | the sample family, no server |

- **Features are written once, in the shared code**, and show up in both
  apps. Agents check them in the Demo app. A feature that needs data to be
  seen gets sample data in `DemoMode.seedIfOn()`, never in the live
  database.
- **The production build is the user's.** They build and install the real
  app from Xcode (`Evlin` scheme) and Archive it for TestFlight. Agents
  don't install the real app on a phone or a simulator to try a feature;
  building the `Evlin` scheme only to check that it compiles is fine.
- **Agents try screens only in the Demo app**, all agents on the same
  simulators: parent side on **iPhone 17 Pro**, kid side on **iPad Pro
  11-inch (M5)**. Don't use the user's iPhone 17 sim or a real phone, and
  don't sign the real app into an account to see a screen.
- The Demo app uses the real app's icon, the original green tile (2026-11-12, the
  user's call: the original only for the app icon; a Demo-only icon, the leaf
  from `Flame_Leaf.psd` on white, was tried and removed the same day). Inside the
  app the leaf on its own is `evlin-leaf-green.svg` (`LeafMark`), on the start
  screen and the opening splash.
- All demo code is behind `#if EVLIN_DEMO` (`App/DemoMode.swift`), which only
  the Demo configuration sets. Never gate demo code with `#if DEBUG`: Debug
  is the build the user runs on real phones. `DemoMode.isBuild` is the
  runtime check; `isOn` and the launch flags only exist in the Demo build.
- The Demo app sends nothing: `APIClient.baseURL` is `https://demo.invalid`,
  sync, outbox and live updates stop short, Sentry isn't started, and the
  Keychain isn't written. It has its own database (no App Group) and
  Keychain, so it can't touch the real app's data on the same device.
- No test data in the live database. `scripts/test_child.py add` refuses
  without an explicit non-live `--database-url`; the Demo app already has
  sample children (Mia, Leo, Ava: most families have two or three; Noah, a fourth, since 2026-11-17, the free trial's example) for multi-child layouts.

## Rules that hold the design together

- **The AI never writes.** Its tools (`draft_task`, `draft_app_block`,
  `ask_follow_up`) pre-fill a card or ask a question. The parent's tap is what
  creates anything. To add a tool, add a module to `tool_calls/`; `chat.py`
  reads only what that package exports.
- **Every task has one emoji** (`tasks.icon`), shown beside it on the kid's
  phone. The chat agent picks it (`draft_task`'s `emoji`, from all of
  Unicode); a typed task gets one on the phone when it's created
  (`Data/EmojiSuggest.swift`, Unicode's emoji names and keywords). Parents
  never see it: only the kid's list shows emoji. The agent writes its
  replies with emoji, Notion-style (see `tool_calls/README.md`).
- **AI features are architecture, not screens.** Don't add UI to inspect AI
  internals (memory, for example) unless asked.
- **The schema change mechanism is `main.py` `_MIGRATIONS`.** It's a list of
  idempotent statements run on every boot; there's no Alembic. Every new model
  or column needs a matching statement there, and an entry in
  `_EXPECTED_COLUMNS`. Tests build from `models.py`, so
  `tests/test_migrations.py` is what catches a missing migration. Postgres-only
  SQL must be checked on a real Postgres.
- **Every approval goes through `routers/occurrences.py` `_review`.**
  That covers the bonus, block resolution, and refusing a double approval.
  Don't add a second path.
- **Live updates are published by a commit hook, not by routes**
  (`live_updates.py`). Reads must not write: a read that writes announces a
  change, which makes the device sync, which reads again. Expiry and similar
  state are computed on read (`blocks.py`), never stored.
- **Apps are Evlin's own catalog rows** (`apps`, `child_apps`), never platform
  identifiers. Blocks point at catalog ids.
- **"Today" and "now" are the child's**, from `children.timezone` via
  `blocks.local_now`, not the server's UTC.
- **Sign in once per phone.** A parent's phone trades its Supabase sign-in
  for its own token (`POST /auth/session`, `app.parent_sessions`); a kid's
  phone has its device token. Neither expires or is renewed: they end only
  on Sign out (`POST /auth/logout`), unpairing, or deleting the account.
  The app signs out only when `/auth/me` (parent) or `/device/me` (kid)
  refuses the token. The server's Supabase client must never hold or renew
  a session (`auto_refresh_token=False`): doing so revoked parents' sessions.
- **Access checks are in the application**, through `access.py`. There's no
  Postgres row-level security. Every child-scoped route must check ownership.

Instant unlock are live, and every `ServerSupport` flag is on in the real app.
The live database was wiped to a clean slate the same day at the user's call
(accounts and all their data; the app catalogue kept); a backup of the app
data from before is in ~/Evlin-backups.

The goal: screens show what's saved on the phone straight away, a tap
changes the screen at once, and the network catches up behind it. Nothing a
parent or kid does is lost to a bad connection or a closed app.

- **One SwiftData store** (`Data/LocalStore.swift`) holds every child (their
  rules and state included), their tasks, today's occurrences, time grants,
  app blocks and policy. Launch hydrates **all** children from it before
  the network answers.
- **"Today" is live.** `CalendarData.todayYear`, `todayMonth` and `dataDay`
  read the clock. `DayClock` notices midnight and a return to the
  foreground on a new day, rebuilds today's lists, and syncs.
- **Retries count once; edits never undo each other** (2026-11-19, the
  user's checklist). Every queued write carries its outbox entry's id as
  `Idempotency-Key` and when it was made as `X-Edited-At`
  (`APIClient.send(_:idempotencyKey:editedAt:)`, from `Outbox.run`). The
  server answers a repeated key from the same caller with the first answer,
  kept a day in `app.idempotency_keys` (`evlin-backend/idempotency.py`, a
  pure ASGI middleware; 5xx not kept), so extra time and blocks, which have
  no phone-made id, are never applied twice. Task edits and the lock flags
  are per field: the phone sends only what changed
  (`Write.taskChanges(from:to:)`, `Child.stateChange`), and the server sets
  a field only if the edit is at least as new as that field's last change
  (`edits.py`, `field_edits` on `tasks` and `child_state`; a future time
  counts as now; no header, as from an older build, counts as arrival).
  `updated_at` on tasks and occurrences. Occurrence status keeps its own
  rules (`_review`: an approval stands, a second one is 409).
- **Leaving the app never loses a write** (2026-11-19, Apple's practice):
  every change and its queued request are saved to disk as they're made
  (`LocalStore.save`, a failure reported to Sentry); each outbox send asks
  iOS for background time when it starts (`Outbox.drain`, `BackgroundWork`,
  `beginBackgroundTask` with an expiration handler that ends it), so a
  parent who taps and leaves at once still has it go out; going to the
  background sends first and fetches only with 10 s or more left
  (`BackgroundSync.finishPendingWork`); a background refresh
  (`com.evlin.ios.refresh`) wakes the app now and then. Not sent in time,
  it's still in the outbox for the next launch or wake-up.
- **Every write goes through the outbox** (`Data/Outbox.swift`): one
  write = one saved HTTP request (`APIClient.Write`), in a `PendingWrite`
  row, sent in order, retried with backoff while offline or while the
  server errors. Screens apply the change themselves first (optimistic).
  A 404 or 409 on replay means the server already has it, so the write is
  dropped quietly. Any other refusal is dropped and reported through
  `SyncState.writeError`. Don't call `APIClient`'s write methods directly
  from a screen: queue them.
- **Creates carry the phone's id.** A task gets its UUID on the phone. The server accepts `id` on create and answers a repeat of the same
  create with the existing row, so a retry never duplicates anything.
  If a server answers a create with a different id anyway (one too old to
  take it), the outbox re-labels the phone's row, the rows that point at it
  and the waiting writes (`LocalStore.adoptServerId`), so the next sync
  doesn't delete it and add it again.
- **Kid writes against a day the phone made up offline** (an occurrence
  materialized locally) name the task and date instead of an occurrence id.
  The outbox finds the real occurrence when it sends.
- **A sync never overwrites a pending write:** it sends the outbox first and
  only fetches once the outbox is empty. Writes are also mirrored into the
  store as they're queued (task created or deleted, occurrence status), so a
  relaunch before they're sent still shows them.
- **Screens read tasks from the database.** `TaskStore` is
  an observed, read-only view of it, rebuilt on every database save
  (`LocalStore.commit`; a sync's writes are one `batch`). A screen never
  edits a copy: an action writes the database (`TaskEdits`, the `mirror…`
  functions) and every screen showing it updates in the same frame. Don't
  keep task lists in `@State`.
- **Syncs merge, and redraw only on change.** Store rows are updated in
  place by id, not deleted and re-inserted, and `TaskStore` only assigns
  what changed. There's no full re-sync after each write: the server's live
  update brings the change back.

Not done yet: children (`FamilyStore`, `Child`) are live objects built from
the database, not read from it on every draw; `SyncState.version` redraws
for changes to the family. The server has no "changed since" endpoint, so a
sync still downloads everything and the phone does the merging. Photo uploads
keep their own queue (`TaskDetailView.upload`).

## Gotchas

- `xcodegen generate` rewrites `Evlin.xcodeproj` from `project.yml`. Settings
  changed only in Xcode, such as the bundle id, are lost.
- SourceKit reports false "cannot find type" errors here. Trust `xcodebuild`.
- A shell-exported `GEMINI_API_KEY` shadows `.env`, because `load_dotenv`
  doesn't override.
- `evlin-tables.sql` is an old design file. It isn't the schema, and
  `init_db.py` can't apply it cleanly.
